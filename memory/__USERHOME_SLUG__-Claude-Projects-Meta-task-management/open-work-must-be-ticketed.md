Any remaining work must exist on the tracker as a **ticket** or a **bug**. A ticket comes from a spec/PRD (`/to-spec` → `/to-tickets`); a bug comes from `/triage`. Naming follow-ons in prose — a HANDOFF paragraph, a "follow-ons" section on a shipped ticket, a chat summary — does not count as capturing them.

**Why:** prose follow-ons are invisible to the frontier-scanning workflow, so they never get picked up and get re-discovered months later. Dan said this after I closed out the open-loop surfacer by listing five follow-ons in `docs/HANDOFF.md` and in ticket 04's notes.

**Dan's actions count as work too (correction, 2026-07-29).** After the parallel wave I listed the owner's remaining steps — authenticate Graph, confirm the O3 notes source, fill `config/dates.yaml`, remove three freed `no-sweep` labels, sign off parity — in PR bodies, PRD comments, and chat summaries. Dan: "shouldn't everything that needs doing, either be me or you, be a ticket?" Yes. A gate on the owner is not exempt from the rule; it is the kind of item most likely to be forgotten, because no agent is scanning for it. Use the `ready-for-human` state label (the repo's five-role vocabulary already carries it) and say in the body **why** it can't be delegated — credentials, personal data, a judgment about his own working surface, a browser-only toggle. A PRD staying open "on owner gates" with nothing ticketed under it is the same invisibility failure in a different costume. Filed as #55–#60, #67, #68, #70.

**The same rule governs DETAIL, not just work items (correction, 2026-08-01).** After recording Dan's direction-1 decision on #123, I flagged the two criteria most likely to bite — "the pinning test must be rewritten, not deleted" and "measure the per-action recording cost rather than assume it" — in the chat summary. Dan: *"surely you wouldn't mention something important only in chat when you know the next agent will not see your comment."* Both happened to be in the ticket body already, but one phrase (`not deleted`) existed only in an issue comment, and the check was worth running. A caveat that changes how the work is done belongs in the **body's acceptance criteria**, where the frontier scan reads it — not in chat, not only in a comment, and not only in a commit message. Chat is a report to Dan; it is never a delivery channel.

**How to apply:** when finishing any piece of work, convert every open item into a tracker item before reporting done. Before writing a caveat into a chat summary, check it is in the ticket body first — and if it is not, put it there rather than saying it twice. Verify each defect against the live store first — the 2026-07-28 pass found the enrich prompt already contained the rule bug 01 was going to "add", and that 3 of bug 03's false positives were suppressed by hand-applied `no-sweep` labels. A bug needing a design decision stays `needs-triage` with the options costed rather than being guessed into `ready-for-agent`. See [[closure-authority-pivot]].
